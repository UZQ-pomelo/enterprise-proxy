## 2. "流量审计"具体怎么体现(三层)

**① 记录层 —— 每次访问都留痕,包括"被拦"与"认证失败"。**
`audit.py` 表结构(requests)16 列,其中审计关键是:
`ts`(精确到秒,可按 `--day` 过滤)· `user/role` · `method/host/url_path/port` ·
`decision`(allow / block_whitelist / block_blacklist / block_category /
block_signature / block_resp_signature / auth_fail / error)·
`rule_id`(如 `category:game`、`domain:*.blocked-site.example`、`req_sig:0`)·
`reason`(人工可读原因)· `bytes_up/bytes_down` · `resp_status` · `cache_hit` · `duration_ms`。

真实记录示例(取自本机审计库):

```
ts 2026-09-03T16:48:04  user employee  role employee  GET  game-site.com /
decision block_category  rule_id category:game  resp_status 403  bytes_up 187  bytes_down 1877
```

→ 可回答:"某员工在何时尝试访问哪个站点、被哪条规则以什么理由拦下、这次
访问产生了多少字节、处理耗时多少"。被拦与异常(502)同样留痕,审计不丢事件。

**② 口径层 —— 计数可复现,不是估算。**
`runtime.py:new_rec` 在任何读取**之前**记下读写计数器基线(`_r0/_w0`)与单调钟
基线;`finish_rec` 用"结束计数 − 基线"回填,故 `bytes_up` 覆盖请求头本身;
CONNECT 隧道的握手与隧道负载经 `_extra_up/_extra_down` 并入;`user/role` 在
请求结束时从连接上下文刷新(认证发生在建记录之后),未认证请求记为 None。
`cache_hit` 标记命中了本地缓存(未触达源站)的请求。响应特征命中发生在
**转发给客户端之前**,审计记录的是"实际管控结果"而非"事后补记"。

**③ 取证层 —— 管理面可查询、可归档。**
`admin.py` 五命令:`report`(总量/决策分布/上下行字节)、`blocked`(最近拦截
明细:时间/用户/目标/规则+原因)、`top-users`/`top-hosts`(按下行流量排行)、
`cache-stats`;均支持 `--day YYYY-MM-DD`。审计库是普通 SQLite 文件
(默认 `data/audit.db`),可拷走归档或用任意 SQLite 工具复核。

## 3. 三个边界与标准答辩答复

> 原则:如实说明边界,不给"全都做了"的虚假印象;每条都给出为什么不是主线
> 硬缺口、以及若要扩展怎么扩展。

### 边界① "客户端必须配代理才能上网"的强制强度

- **是什么**:本实现是标准**显式正向代理**——流量只有显式配置代理后才经过本
  系统(curl `-x`,浏览器手动代理)。它在功能上满足"配置才受管控/审计";
  但单机演示中演示站点与代理同机,不配代理也能直连到演示站,做不出
  "不配代理就断网"的系统级强制画面。
- **为什么不是缺陷**:HTTP 正向代理的标准语义即是客户端侧显式配置;强制
  "必然走代理"在企业里由**浏览器策略 / PAC 自动配置 / 网关透明代理**完成,
  不属于代理进程本身职责。题目语境"客户端必须配置该代理服务器"描述的正是
  正向代理的接入方式。
- **答辩口径**:"我们的系统是标准正向代理——员工机把 HTTP/HTTPS 代理指向
  `127.0.0.1:18080` 后,所有 web 流量才进入本系统被解析、拦截与审计;演示中
  curl 的 `-x` / 浏览器的手动代理即代表这一接入。企业若要杜绝员工绕过,
  用组策略下发 PAC 把代理配置固化,使'经代理'成为事实唯一路径。"
- **如需更强的现场对比**:视频里可先用浏览器无代理访问演示站"可达"、再展示
  "配置代理后同一访问被审计+按角色管控"两条路径的差别,说明系统管的是
  "经代理的通道"。

### 边界② HTTPS(隧道)只能审计到连接级

- **是什么**:CONNECT 隧道建立后代理只做字节泵送,因 TLS 加密**无法看到内部
  URL 与内容**;审计记录为 method=CONNECT + 目标 host:port + 上下行字节,
  不含内部路径。
- **为什么不是缺陷**:任何不做 TLS 中间人解密的正向代理均如此,题目未要求
  解密加密流量;明文 HTTP 请求仍是全量解析审计。企业要内容级 HTTPS 审计
  需部署 MITM(下发企业 CA),通常属于更大的合规工程。
- **答辩口径**:"HTTPS 会话我们审计到'谁在何时连向哪个站、多少流量'这一连接
  级;URL 与正文因 TLS 不可见,这与所有非解密型正向代理一致。如需内容级
  审计,可扩展为 TLS 中间人(企业 CA + 会话密钥解密)模式。"
- 数据佐证:隧道字节经 `_extra_up/_extra_down` 精确并入审计行(见 runtime
  口径),即"流量多大"是记全的。

### 边界③ 特征扫描的覆盖面

- **是什么**:请求特征目前扫描 **URL 与请求头**(覆盖题目示范的 `password=`
  明文外泄检测),**不扫 POST 正文**;响应特征只对**可整体缓冲的 text/* 且
  ≤2MB** 的响应体生效(更大的/流式的体做实时转发,不做内容检查)。
- **为什么不是缺陷**:题目要求的"特定特征数据"以 URL/头/正文三类为示范,
  请求侧 URL+头、响应侧正文均已实现并有对应测试;正文检查只对可缓冲的小
  文本做,是保代理低延迟的工程取舍,已在设计文档注明。
- **答辩口径**:"特征分两侧:请求特征扫描 URL 与请求头(防口令随 URL 外泄),
  响应特征对可缓冲文本做正文检查并就地拦截;POST 正文扫描与流式内容检查
  是已预留的扩展点。"
- **若要扩展**:请求侧把分类后暂存的上行体并入特征扫描(当前实现已按 CL/
  chunked 读取客户端体并中继,只需在缓冲副本上跑同一签名表)。
